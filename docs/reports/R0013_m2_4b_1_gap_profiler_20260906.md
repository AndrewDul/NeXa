## INSTRUMENTATION ARCHITECTURE

Everything **observes** the frozen M2.4 pipeline through hooks that already
existed or are additive, default-`None` callbacks. No second conversation
session, model client, TTS scheduler, audio queue, or media pipeline.

```
probe callbacks (unchanged names)          NEW measurement wiring (only with --report)
────────────────────────────────           ─────────────────────────────────────────────
on_user_transcript  ───────────────────▶   MetricsCollector.start_turn(stt text/latency)
on_assistant_token  ───────────────────▶   .first_token() / .assistant_token(char count)
on_assistant_complete ─────────────────▶   .assistant_complete(text)   (real char length)
on_conversation_error ─────────────────▶   .conversation_error(exc)

TtsStatusObserver (M2.4, + 5 optional None-default callbacks):
  on_tts_started / on_tts_first_audio / on_tts_stopped / on_tts_error   (existing)
  on_tts_audio(bytes, rate, ch)      ──▶   .tts_audio()     in-memory byte accounting only
  on_tts_text(text)   [TTSTextFrame] ──▶   .tts_text()      per synthesized sentence
  on_tts_response_end [downstream    ──▶   .tts_response_end()  turn's TTS truly finished
      LLMFullResponseEndFrame]
  on_bot_started/stopped_speaking    ──▶   .bot_started/stopped_speaking()  playback spans

background daemon thread (report only):
  ResourceSampler(period 400 ms) ── /proc + sysfs (+ vcgencmd get_throttled every ~2 s)
```

- **`src/nexa/voice_tts/metrics.py`** (new module) — all metric math:
  `TtsSegment`, `TtsTextChunk`, `PlaybackSpan`, `BufferEstimate`,
  `ResourceWindowSummary`, `TurnMetrics` (composes the existing lean
  `TurnTiming`, does not duplicate it), `diagnose_dominant_wait`,
  `MetricsCollector` (FIFO turn correlation, same rule as
  `TurnTimingTracker`), `render_turn_report`, `TurnReportJsonlWriter`, and
  the report-mode-only `ResourceSampler` / `read_raw_proc_snapshot` /
  `summarize_resource_window` (pure, injectable readers → unit-testable
  without hardware).
- **`src/nexa/voice_tts/bridge.py`** — `TtsStatusObserver` gains 5 optional
  `None`-default measurement callbacks; every frame is still forwarded
  unchanged. Omitting them (the M2.4 default) is the M2.4 observer exactly.
- **`src/nexa/voice_tts/timing.py`** — `TurnTiming` gains one field
  (`assistant_text_chars`); `assistant_complete()` gains an optional
  `text` arg. Passing nothing keeps M2.4 behaviour.
- **`apps/nexa_voice_tts_probe.py`** — `--report`, `--report-json PATH`,
  `--report-sample-ms N`. When absent, `_metrics is None` and every hook is
  a no-op. The report path pushes **no frames** (ast-guarded test).

**Turn finalisation.** A turn is finalised on the downstream
`LLMFullResponseEndFrame` — which Pipecat emits only after that turn's
audio context has drained — **provided playback has also settled**. Real
hardware showed the end frame can arrive while a `BotStarted` span is still
open (the transport's final `BotStoppedSpeakingFrame` comes later); the
collector then defers finalisation to that trailing `BotStopped`. `close()`
flushes anything still in flight at shutdown. Emit is single-point
(`_finalize`) — the per-turn report prints and the JSONL line is written
exactly once.

**`diagnose_dominant_wait` heuristic** (documented as heuristic, not truth;
tuned against the R0012 profiles):
- `FIRST TOKEN` if `first_token_latency_s ≥ 3 s` and (≥ 40 % of the turn's
  spoken span, or the span is unknown).
- `LLM TEXT PRODUCTION` if total silence-gap ≥ 1 s **and** ≥ 1 buffer
  underrun **and** mean synth RTF < 0.6 (synth was fast, LLM wasn't).
- `TTS SYNTHESIS` if mean RTF ≥ 0.85 and total gap ≥ 1 s.
- `OUTPUT UNDERRUN` if underruns and gaps but LLM and synth were both fast.
- else `UNKNOWN`.

## BUFFER ESTIMATE VALIDATION

`buffered_audio_seconds ≈ Σ(TTS audio bytes) ÷ (rate·2·ch) − (now − first_audio_at)`
— R0012 flagged this `INFERENCE`. Validated with
`docs/research/m2_4b_speech_flow/buffer_validation.py` (the real
`AssistantSpeechBridge → PiperHttpTTSService → TtsStatusObserver →
LocalAudioOutputTransport` path, scripted steady token feed, 200 ms
periodic sampling), raw:
`docs/research/m2_4b_speech_flow/buffer_validation_raw_20260906.txt`.

| feed | BotStopped events | buffer max | underrun events | estimate at each real BotStopped | `estimate_vs_real_stop_error_s` | real audible gaps |
|---|---|---|---|---|---|---|
| 3 tok/s (LLM ahead of speech) | 1 @ +28.6 s | **11.1 s** | 1 @ +28.6 s | **−0.0 s** | **0.0 s** | none |
| 2 tok/s (LLM ≈ speech) | 4 (3 s-timeout splits) | 5.6 s | **0** | +4.9 / +4.3 / +4.1 / +3.6 s | n/a (no underrun) | **none** (`gaps_ms=[0,0,0]`) |

**Findings:**
1. **The estimate tracks reality.** When it reaches ≤ 0 the audio has
   genuinely stopped — at 3 tok/s the crossing landed at the *exact*
   `BotStoppedSpeaking` instant (error 0.0 s, bounded only by the 200 ms
   sample period).
2. **The 3 s-`stop_frame_timeout_s` `BotStopped`/`BotStarted` churn is
   cosmetic, not audible, while the buffer holds.** At 2 tok/s the pipeline
   emitted 4 `BotStopped`/`BotStarted` cycles but the estimate never fell
   below +3.6 s and there were **zero** real inter-span gaps. So a raw
   `BotStopped` count over-reports "stops"; the estimate + `silence_gaps_ms`
   (positive gaps only) is the honest signal.
3. **Fixed a spurious-underrun bug during validation:** the observer fires
   `on_tts_first_audio` *before* `on_tts_audio` for the first frame, so
   sampling at `first_audio` read `total_audio_seconds == 0` → a false
   underrun. The first buffer sample is now taken in `tts_audio()` once
   real bytes are counted (regression test added).

**Not promoted to a control signal** (M2.4B.3's job, gated on operator
A/B). It is accurate enough to *diagnose*, which is all B.1 needs.

## OLLAMA METADATA FINDINGS

Per the task: inspected `nexa.providers.ollama.LocalModelProvider.generate()`.
It streams **only the `content` string** of each `/api/chat` chunk and, in
the `done` branch, checks `chunk.get("done")` but **discards** that chunk's
`load_duration` / `prompt_eval_count` / `prompt_eval_duration` /
`eval_count` / `eval_duration` / `total_duration`. Its contract is
`AsyncIterator[str]`.

Exposing that metadata cleanly to the probe would mean threading an
optional callback through **`providers/base.py` (the ABC) →
`providers/ollama.py` + `providers/llama_server.py` → `conversation/session.py`
→ `conversation/streaming.py` (or `VoiceConversationAdapter`)** — the
canonical, frozen `ConversationSession` path. **That is beyond
instrumentation-only scope, so it was NOT implemented here** (the task says
to stop and report before an invasive provider change). No second Ollama
request was added.

**Minimal additive design for a separate small task** (no behaviour
change): add `on_final_metadata: Callable[[dict], None] | None = None` (keyword-only,
default `None`) to `ModelProvider.generate`; the Ollama worker, in its
existing `done` branch, calls it once with the timing fields via
`loop.call_soon_threadsafe`. The yielded text stream is byte-identical; no
existing caller passes it. `ConversationSession.send()` would forward a
caller-supplied callback. Recommended for the **first-token latency
investigation track**, not for B.2.

In `--report` mode B.1 therefore captures, in-product: first-token **wall**
latency, generation duration, real **char** count, and chars/s. The
Ollama `done`-chunk numbers (`prompt_eval_s`, `eval tok/s`, `load_duration`)
come from the standalone
`docs/research/m2_4b_speech_flow/first_token_contention.py` (its own
`/api/chat` request — a research harness, not the product path).

## SYSTEM RESOURCE SAMPLING

`ResourceSampler` — one daemon thread, default **400 ms** period.

- CPU%: `/proc/stat` + `/proc/<llama-pid>/stat` (utime+stime) deltas;
  `SC_CLK_TCK` via `os.sysconf`.
- Temp: **`/sys/class/thermal/thermal_zone0/temp`** (a file read — the
  earlier `vcgencmd measure_temp` subprocess cost ~5 ms/sample).
- Throttle: `vcgencmd get_throttled` (the only source) — the sampler asks
  **at most every ~2 s** and carries the value forward between reads.
- Memory / swap: `/proc/meminfo`.
- `llama-server` PID: `pgrep -f llama-server` once at start; if the
  per-proc read fails for 3 samples (Ollama respawns the backend on a model
  reload → new PID), it is looked up again.
- Overlap flags (`stt_active` / `tts_active` / `generation_active`): a
  shared `ActivityFlags` the collector + probe update. `stt_active` is a
  **proxy** — set between `VoiceState.END_OF_TURN` and the transcription
  result (when whisper.cpp runs); no "STT started" hook exists.

`window_summary(start, end)` returns the per-turn `ResourceWindowSummary`
at finalisation; `throttled_any_hex` = bitwise-OR of every mask seen in the
window.

## FIRST-TOKEN CONTENTION RESULT

`docs/research/m2_4b_speech_flow/first_token_contention.py`, raw:
`docs/research/m2_4b_speech_flow/first_token_contention_raw_20260906.txt`.
Controlled, product model unchanged.

| scenario | first-token (wall) | `prompt_eval_s` | `gen_tok_s` | `load_s` | llama-server CPU% | notes |
|---|---|---|---|---|---|---|
| **A** idle system | run 1 **33.5 s**, run 2 0.64 s | 0.6–2.1 | 3.1–3.2 | **run 1 = 31.4 s** | n/a¹ | run 1 = full model **reload** (idle keep-alive expired) |
| **B** Piper up, idle | **0.63–0.73 s** (4/4) | 0.62–0.72 | 2.6–3.1 | 0 | **mean 365 %, peak 395 %** | warm, uncontended baseline |
| **C** Piper synthesising concurrently | **16.2 s** | **16.2 s** | **0.15** | 0 | — | prompt-eval **24×** worse, tok/s **19×** worse |

¹ the sampler lost the `llama-server` PID across the reload (new backend
process); the re-lookup fix landed after this run.

**Conclusions — two distinct first-token causes, both measured:**

1. **Model eviction + reload is the dominant "tens of seconds" stall.**
   `NeXa`'s Ollama provider sets `keep_alive="5m"`; after a quiet gap the
   next turn pays a **~31 s** cold model load (`load_duration` 31.4 s,
   `first_token` 33.5 s). This matches the operator's report and is an
   **LLM-serving** problem — **not** speech-flow, **not** to be masked with
   a filler. Candidate fix (separate track): a much larger `keep_alive`
   (e.g. `30m`/`-1`) so a conversational pause never triggers a reload.
2. **Concurrent Piper synthesis really does starve generation** —
   confirming R0012's `INFERENCE`. With Piper synthesising in a loop,
   gemma4:e4b `prompt_eval` went **0.66 s → 16.2 s** and generation
   **~2.9 → 0.15 tok/s** on the 4-core Pi. Real M2.4 issues ~1 Piper
   request per sentence (not a loop), so the live effect is milder, but the
   mechanism is unambiguous. Levers (separate track / ADR-0003 D7):
   sequence TTS synthesis away from the LLM's prompt-eval window; M2.4B.3
   batching (fewer, larger Piper requests) reduces synth frequency.

**Warm, uncontended baseline: first-token ≈ 0.65 s, generation ≈ 2.9 tok/s**
(scenario B) — consistent with R0009/R0010. No swap growth, no thermal
throttle (`0x0`, ≤ 67 °C) in any scenario.

## ANYTHING DISPROVED / REFINED FROM R0012

- R0012's "**CPU contention** … the dominant cause of the *worst* stalls":
  **refined.** The worst *first-token* stalls measured here are **model
  reload** (`load_duration` ≈ 31 s), a separate mechanism. Contention is
  real and severe for **prompt-eval and tok/s** (scenario C: 24× / 19×),
  which *is* what starves the audio buffer mid-reply. Both are LLM-layer,
  both stay off the speech-flow track.
- R0012 counted `BotStopped`→`BotStarted` cycles as evidence of audible
  stop/start. **Refined:** while the buffer holds (validated ≥ +3.6 s at
  2 tok/s), those cycles produced **no** audible gap. The honest audible
  signal is `silence_gaps_ms` (positive gaps between playback spans) +
  buffer underruns, not the raw `BotStopped` count. B.1's report separates
  the two.
- R0012's buffered-audio estimate (`INFERENCE`): **validated** — error
  0.0 s at the real BotStopped for the 3 tok/s case; no false underruns at
  2 tok/s (after fixing the first-audio sampling bug).
